## 运行边界

用户可以在台式机和笔记本上各自离线采集。只有设置服务地址、授权设备并选择本机数据范围后，客户端才向该服务传送统计。部署者控制域名、身份服务、数据库、邮件及备份。Phase 3 的用户操作包括管理设备、查看同步状态/待核实记录、手动维护项目和任务组。账单、费用和客户财务留在各自阶段。

| 组件 | 责任与依赖 |
| --- | --- |
| 已验收采集 Worker / 托盘 | Worker 是 Tracker 统计库的写入者；原生列表继续从本机读取，云端中断不影响采集和显示。 |
| 拟新增 Windows 同步进程 | 使用登录用户权限，只读 Tracker SQLite v2；在独立 SQLite 中记录授权范围、Outbox 和下载缓存。复用既有宿主管理思路，按需启动，区分“暂停同步”和原有“暂停监控”。 |
| 拟新增管理入口 | 配置自托管 HTTPS 地址；用系统浏览器完成账号操作及设备授权；显示上次成功同步、待传数量、异常与归属待核实项。允许用户显式关联不同 Session 到同一任务组。 |
| 自托管 ASP.NET Core API | 单一部署单元内区分账号、设备、同步三个职责。Identity 负责本地账号；成熟 OAuth 实现负责桌面授权。API 执行设备撤销检查、租户授权、幂等和字段准入。 |
| PostgreSQL | 事务保存来源证据、规范事件、用户编辑和可拉取变更。以账号作为隔离和提交排序边界。查询投影可以重建。第一版无消息队列依赖。 |

采用独立同步库的原因是 v2 的扫描检查点和投影已封装在 Worker 事务中，且投影会因父日志晚到或重放而修订。只增读新行会漏掉撤回。在第二个本地库对一致快照做差分可保持采集器原状，并允许同步进程任意崩溃后续传。代价是增加磁盘读取和本地清单空间，首轮必须测量大型历史库的读取时长和 WAL 增长。[现有统计库](database.md) · [差分与恢复细节](phase-3-data-sync.md)

| 顺序 | 工作与前置项 | 完成证据 |
| --- | --- | --- |
| 1 | 冻结协议 v1、统计字段、账号隔离键、事件键测试向量和脱敏样本；选定受维护的 .NET、PostgreSQL 与认证库版本，核对 MIT 发布所需第三方许可与告知 | 两个独立实现对同一事件给出同一键；字段审查通过；锁定依赖与许可证清单 |
| 2 | 在隔离环境建立自托管 HTTPS、Identity、邮件、设备授权及最小 PostgreSQL 结构；分别使用迁移账号和受限运行账号 | 注册、找回、两机授权、撤销、跨账号拒绝均可复验 |
| 3 | 交付本地只读适配器与账号分区 Outbox；先用测试接收端验证离线积压、差分、修订、退出恢复 | 原有回归通过；上传载荷仅含白名单；账号切换与未授权历史隔离 |
| 4 | 实现云端事务回执、事件级归并、旧快照隔离、修订/撤回和模型/耗时投影 | 重复、乱序和丢 ACK 后统计收敛；同键异值可追溯 |
| 5 | 交付 pull、快照换代、项目与任务组版本控制、设备及同步状态入口 | 两机和新安装下载相同规范数据；并发编辑保留双方意图 |
| 6 | 在自托管预发布环境演练断网、恢复、升级与回滚，封存测试证据并提交负责人 | 按[验收矩阵](phase-3-acceptance.md)逐项签收，记录复现方式、实际分母及遗留风险 |

## 自托管部署与运维设计

- **交付形态。** 计划提供可从源码构建的版本化 API 镜像、固定摘要的 Compose 示例、配置样例和 PostgreSQL 迁移包。单机可用 TLS 反向代理、API、PostgreSQL 和自选 SMTP；也可接部署者现有反向代理、数据库及邮件服务。客户端以部署者的 HTTPS issuer 识别服务，无中心许可、域名或托管账号依赖。
- **首次部署。** 配置持久卷、域名、公网或内网受信任证书、固定 issuer、数据库连接、SMTP 发件地址和注册策略。初始仅部署者可启用注册或发邀请。数据库只开放给私网 API；代理覆盖外来的转发头，应用仅信任指定代理。密钥挂载为受限文件。执行一次迁移作业，API 就绪检查验证 schema、密钥可读及数据库连接，再开放流量；部署者用两个测试账号验证隔离与收信。认证链接使用预置外部域名生成。
- **持久材料。** PostgreSQL 保存所有账号及同步状态。Identity Data Protection 密钥环、OAuth 签名/加密密钥、恢复控制记录及域名配置独立持久化；密钥备份加密、与数据备份分权保管。轮换时保留旧解密材料到有效期结束。SMTP 凭据和备份加密密钥由部署者的密钥库管理。
- **备份目标。** 建议个人部署起点为每日基础备份、连续 WAL 归档，目标 RPO 15 分钟、RTO 4 小时；在目标机器上按实际体量演练后签收。保留最近 30 天的离机加密副本，定期抽样恢复并核对校验和、迁移版本、账号隔离、规范事件及关联。同步请求体、标题和诊断正文不进入运维日志。
- **服务端恢复。** 关闭公网流量/写入，在隔离新实例恢复数据库至指定时间点；校验外键、账本、项目版本与提交游标。每次回滚到历史时间点都生成全新恢复代际，作废既有设备访问/刷新授权、浏览器会话及未完成的授权/找回链接；恢复点之后的解绑等安全操作以独立、持久的安全审计/撤销记录为准。缺失记录时保持账号和设备冻结，由部署者核实身份后逐个重新启用，防止旧密码或授权复活。重新签发凭证，客户端按新代际重建缓存、核对已确认来源并补传差集。恢复点之后仅存于云端且各客户端也无副本的变更，列入恢复缺口。记录实际丢失区间和恢复时长。[客户端恢复流程](phase-3-data-sync.md)
- **客户端恢复。** 使用 SQLite 在线备份或干净停机后备份本机统计库、同步清单与队列到用户控制的加密介质；有 WAL 时在线复制单个主文件不能作为一致备份。本地备份不进入同步 API。身份凭据独立存储。原机恢复先对齐云端来源版本；换机重新授权、使用新设备身份。仅恢复云端快照可取回规范统计和人工关联，v2 本机证据与未上传事件的恢复依赖本地备份。原始 Codex 日志由用户自行管理。
- **升级及回滚。** 先备份，在备份副本试跑迁移及上一版客户端兼容测试。采用先扩展、后迁移数据、最后移除旧字段的次序。协议能力通过版本协商；不兼容的客户端停传并保留 Outbox。兼容 schema 时可回退应用版本；需要回退数据库时执行上述恢复换代流程。监控只暴露请求数、延迟、积压时长、失败类别、备份归档滞后等指标。

候选版已提供本机可运行的客户端和服务端。部署规模、备份目标及正式签收由现场演练确定。[运行手册](phase-3-run.md) · [实施结果和待验项](phase-3-implementation.md)
